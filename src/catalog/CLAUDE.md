## Catalogs (`src/catalog/`)

The thing a team already has is not a flow. It is a requirements page, a QA checklist, a spreadsheet of cases, a PDF spec. `wowlidator catalog <file>` is the path from that to a test, and it is **two steps with a gate between them**:

```
document ──► claims ──► (a person prunes) ──► cases ──► a run each
```

**The gate is the point.** Handing a whole document to a model and running whatever comes back spends tokens and a browser on work nobody has looked at, against claims the model may have read out of a heading. Claims extraction is one cheap call and no browser; a list of sentences is something a person scans in seconds. `--claims-only` stops there and writes a claims file; `--claims <path>` authors from what survived. Running it in one go is allowed and is the wrong default — the panel never does it.

**Claims extraction is not authoring.** It asks only *what does this document assert*, never *how would you test it* — no selectors, no steps, no page. Grounding stays where it is already solved: `FlowAuthor` writes the steps against a live AX tree, so selectors come from the page rather than from the document. Routing reuses the `generator` role for the same reason `src/repair/` does — a large prompt in, a small flat shape out.

**Every listed case is reported, including the ones that could not be run.** `runCases()` in `src/cli/run-cases.ts` is the one loop behind both `catalog --run` and `generate --run`: it runs the list, prints one roll-up line per case, writes the suite index, and returns outcomes for `suiteExit()`. Three verdicts, not two — `passed`, `failed`, and **`blocked`**, which means the case produced no verdict about the application at all.

- **A dead browser is not an exception, it is a bundle.** `runFlow` catches a failure to attach and returns a bundle with status `failed`, zero steps and the error on it — so a `try`/`catch` around the call almost never fires, and every case after the browser went away was reported as a red ✗ with nothing under it. Read literally that says the application broke in seven new ways. `neverRan(bundle)` is the real test: **the run failed but no step of it did**, so either nothing ran or it broke off with no assertion contradicted. (The `try`/`catch` stays for the narrower case of something throwing before there is a bundle.)
- **Blocked is not failed**, the same distinction `proofs-to-artifacts.py` makes for a step that never ran: scoring the harness's own gap as a defect sends someone hunting a bug nobody claimed existed. It is not a pass either — `suiteExit` returns `EXIT.failed` if anything really failed, else `EXIT.environment` if anything was blocked, else `ok`. Sibling of `exitCodeFor`, which does the same for a single run by matching the error string; this one decides structurally and so also catches a browser that died mid-run.
- **Blocked cases appear in the suite index** (`BlockedEntry`), listed first, counted in the denominator, linked to their report when one was written. An index showing 7 rows for a 10-case suite reads as a 7-case suite, and "7/7 passed" is a lie the reader has no way to catch.
- **Every non-pass line says why.** A bare ✗ was the worst of both: it read as a defect and gave nobody anything to act on. Reasons are trimmed to their first line — the attach error carries a two-line "start Chrome like this" hint, and seven of those turn a ten-line summary into a wall.

Still open: JUnit/CTRF count a blocked case as a 0-test suite, so CI sees it as absent rather than as blocked. `neverRan` is the seam to fix that through.

**A catalog authors discrete cases, and each is run on its own — one failure is noted, never fatal.** A document asserts several independent things; a flat step list stops at its first failure, correctly, because everything after it is in an unknown state. Put six approved claims in one flow and the second failure leaves four claims unanswered while the report shows only the one that broke — the exact opposite of what the review gate was for. So the authoring prompt asks for one case per claim, `AuthoredStepSchema.case` labels which case each body step belongs to, and `splitIntoCases()` partitions the body; the CLI turns each case into its own flow (**sharing `setup` and `teardown`, which is what makes a case independent of the one before it — setup runs again before each**), runs them all, and prints a roll-up plus a suite index. Same principle as `fillEach`, one level up. Three rules hold the split honest:

- **Consecutive steps with one label are one case, and order never changes.** Two runs of the same name are two cases (`rows`, `rows (2)`), because gathering them would move steps past ones they depend on.
- **A case with no assertion is not a case** — it is preparation for the case that follows, or cleanup for the one before, and is folded into that neighbour. Run alone it would pass whether or not the feature worked. A body that asserts nothing *anywhere* is handed back whole so `FlowAuthor` refuses it as it always did.
- **`case` is the one authored field a step may decline to fill.** It decides how the body is divided, not what any step does, so a model that omits it costs the isolation between cases and not the whole authoring call: unlabelled everywhere is one case, byte-for-byte what this produced before cases existed. That degradation is what the `LlmFlowAuthorModel` payload in `tests/flow-author.test.ts` exercises. It is expressed as **`z.string().nullable()` behind a `z.preprocess` wrapper**, not `.default('')`, and the split is load-bearing in both directions: zod emits a defaulted field as *absent from* `required`, which strict providers reject outright (see [Structured output on free tiers](#structured-output-on-free-tiers)), while a plain `.nullable()` would put the key in `required` and then reject the lenient provider that drops it — the very degradation this field exists to allow. The wrapper emits the `.nullable()` schema and fills a missing key with `null` on the way in, so both halves hold.

**A claim marked `testable: false` is kept and never checked.** "The user is signed in as an admin" sets up the claims around it; dropping it loses what they depend on, and turning it into an assertion reports a failure about a precondition. It goes into the authoring prompt under *assume this is already true*.

**Context documents are a second input, labelled apart from the catalog.** `--context-doc` is background the model may read to understand a term; it asserts nothing and is never a source of claims. The two are separate sections in both prompts for the same reason a probe report is kept apart from the AX tree in `flow-author.ts`: a model that conflates them writes claims about the API documentation instead of about the application. Note the flag is **`--context-doc`, not `--context`** — the latter already means the static repository index, and two things called context would be one flag away from silently doing the other's job.

**A context document is cut to the part that bears on the case** — `src/catalog/retrieve.ts`, **on by default at `CONTEXT_BUDGET_CHARS` (24,000 characters)**, `--context-budget 0` sends every document whole. The problem is real: `authorEachRow` authors each table row in its own call, so whole context documents are multiplied by the row count, and a twelve-row sheet with one 120,000-character spec spends ~360k input tokens on background, eleven-twelfths of it about rows that call is not writing. Selection is **BM25 over heading-aware chunks** — no model call, no dependency, no key, because the query is the row's own steps and the claims prompt already says to use the document's own words, so query and corpus share vocabulary by construction. Measured on a 60,000-character spec across four rows: 94% less background, each row quoting exactly its own section.

**It was opt-in until 2026-08-21 because it decides what every authoring prompt sees**, and an inaccurate context poisons every test written from it. The first cut shipped it on and broken; it went off while the rails below were built; and it is on again because the measured cost of off was the thing people hit: two spreadsheets remembered on a repository (1,014,914 + 78,752 characters) cost ~50,000 input tokens of background on *every* authoring call of a ten-row sheet, and the same rows retrieve to 15–25k characters (~4–6k tokens), each quoting its own sections. Five rails, four of which exist because a defect got past the first round of tests:

- **A heading is Markdown's `#` and nothing else.** The first version also read a numbered line as a section ("3.2 Session timeout"), guarded on length and a trailing full stop — and that guard was worthless, because an ordinary procedure step ("1. Open the probation hub") satisfies it exactly. A heading's line is carried as `headingPath` and never as body, so **every step of every numbered list stopped existing**: a six-step checklist chunked to *nothing at all*, and the model was handed an outline of the steps with no steps under it. The regression test asserts the real invariant — no line of a document is lost by chunking, across five document shapes — which is the same rule `extract.ts` states as "never hand back text that is not in the document", pointed at the other direction.
- **Selection only engages on a document bigger than the budget.** Under it there is nothing to save and everything to lose: the outline and the notice make the prompt *larger*, and the model reads quoted fragments where it used to read the author's own prose. Found by measuring — a 15,112-character spec came back at 15,657.
- **A query that does not tell the sections apart selects nothing** (`DISCRIMINATION_MIN`). Measured on a spec whose sections share their vocabulary: every chunk scored 0.06, the tie broke on document order, and the "selected" sections were 1–7 — *positional truncation wearing a relevance badge*, which is worse than positional truncation because a reader believes it. Below the ratio the document is sent whole and the note says why.
- **A chunk must score `RELATIVE_SCORE_FLOOR` of the best chunk to be quoted.** Filling the budget with whatever ranked next is how one row's prompt ended up carrying nine sections about other rows and calling it relevance.
- **The spine — the document's complete heading outline — is sent whatever the budget**, with an elision notice worded after `captureAxTree`'s ("do NOT conclude anything is missing"). Retrieval's characteristic failure is *silent partial recall*: an unselected section reads exactly like one that does not exist. Each document is guaranteed its best-matching section however small the budget, and a document nothing was left out of is returned unchanged — no outline, no notice, nothing to disclose.

Containment degrades the **opposite** way from history and coverage: a failure anywhere inside returns every document whole. Those are diagnostic, so failing to nothing is right; this is an optimisation, so it fails to everything. It is pointed at supporting documents only — never the catalog itself, never `draft`'s `--- SOURCE:` material, never the AX tree, because those are enumeration problems and you cannot retrieve a claim you do not yet know exists. There is a test per boundary. Context documents are read past `DEFAULT_MAX_CHARS` only while a budget is set, so with it off, extraction is exactly what it was.

Two tokenising details worth keeping: `PB-05-01` is indexed **whole and in parts** (a case id is the highest-signal token these documents contain), and a script with no word boundaries — Thai, Han, Kana, Khmer, Lao, Burmese — is indexed as **character n-grams**, because a whitespace tokeniser makes a Thai section one token and retrieval returns nothing for it however well it matches. The IDF is the smoothed `ln(1 + (N - n + 0.5)/(n + 0.5))`: the textbook form goes negative on a small single document, so a chunk scores *worse* for containing a query term. Ranking was never the cost — 60 chunks rank in 9ms — so there is nothing here a faster algorithm would buy. Design and verdicts in `docs/context-doc-retrieval-spec.md`; tests in `tests/context-retrieval.test.ts`.

**The claims file is the gate as a file.** Plain JSON, one `approved` boolean per claim, so the review can happen in an editor, in a diff, or in a browser without any of those being the only way — and so what ran is a file you still have afterwards. Everything starts ticked: a gate that begins empty is one everyone clicks "select all" through. An absent `approved` key means approved, so a hand-written claims file does not have to say yes to every line.

### Cases run together (`src/cli/case-plan.ts`, `runCases`)

A catalog's cases are independent by construction (`setup` re-runs before each), so nothing about the harness requires them to run one after another — and one after another they spent most of a 9-minute run holding a browser open while the machine idled. `runCases` now runs them through `runWithConcurrency`: `--concurrency N` (default `DEFAULT_CONCURRENCY` 4; **`1` is byte-for-byte the old sequential run, untagged output included, and is the A/B test for a parallel result that looks wrong**). Outcomes are collected **by index, never appended**, so the roll-up, the suite index and the exit code read as the list someone approved rather than as a stopwatch result.

**The application can require serialisation even when the harness does not.** `caseWrites()` classifies each case; a writer runs with nothing else in flight — alone, not one-of-four. It errs toward "writer" in every ambiguous shape but one: a non-GET `request`, any `expectDb*`, a `fill` on a page that is not a sign-in URL, and a `workflow` goal that names a mutating verb (`WRITE_VERB`) are writes; signing in is not (the session is per-context), and a workflow goal that only navigates, opens or reads is not — measured, five of six cases were serialised for goals like "navigate via Sidebar → Team → Probation Reviews" before that refinement. **The auth exemption reads the URL, never the field name**: the first cut matched `email|password|username` in the selector and called "Manager email" on a business form a login. A `when` step's branches are inspected too.

Two things had to change underneath for it to be safe. `SmartRunnerOptions.isolate` gives an unfilmed run its own context, carrying the browser's session the way the recording path already does — `--video off` used to share `browser.contexts()[0]`, and parallel cases would have clicked in each other's tabs. And `SmartRunnerOptions.inheritSession` lets `runFlow` decide from the flow's own shape (`signsInItself`): a flow that types a password starts from an **empty** context, recorded on the bundle's `notes` — a stale admin session left in the browser by an earlier run had put an HRBP case on the admin landing page before its first step. The healed-selector cache's `flush()` **merges with the file on disk** (only this instance's touched keys win; the temp name carries a counter — it was named by PID, identical for every parallel case, and last-writer-wins dropped repairs that had just been paid for), and `RunHistory.append` is serialised per file.

**A catalog's cases run as they are authored** (`CaseQueue` / `runQueue` in `case-plan.ts`; `authorEachRow`'s `onCase` hook). Authoring a row is a model call the browser spends idle, and running a case is browser time the model spends idle; the old order — author all twelve, then run all twelve — paid both waits in full. With `--run` and a concurrency above 1, `cmdCatalog` stamps and writes each case the moment its row is authored and pushes it into a queue `runCases` is already draining, so the first case is usually proved before the last row is written. The queue keeps every rule the fixed list had: items are indexed by arrival (sheet order, so outcomes still read as the approved list), a writer arriving mid-run waits for the pool to drain and runs alone, and `runWithConcurrency` is now literally a closed queue. **Concurrency 1 authors everything first**, byte-for-byte the old order, and is the A/B for a pipelined result that looks wrong. The producer owns `close()` in a `finally`, and an authoring crash awaits the runs already in flight before the error lands — a refused row must never leave the consumer waiting on a list that will not grow, and a queued case must never be abandoned with its proof half-written. The roster prints one line per case as it starts (`  [cN]      alone|shared  name`, the exact shape `jobs.ts` parses), so wowUI grows a row per case rather than waiting for a list that does not exist yet.

**Rows are authored in a pool too** (`--author-concurrency N`, default `DEFAULT_AUTHOR_CONCURRENCY` 3; `mapPool` in `case-plan.ts`, `withPages` beside `withPage`). Authoring a row is mostly waiting on a model, and twelve rows used to wait one after another. Each worker owns a start tab of its own — the AX read alone would be safe to share, but `--probe` and the capture pilot *act* on the start page — while the per-row journey capture was already in a fresh context (`openCaptureTab`). Starts stay in sheet order and the returned list is compacted back to sheet position, so the authored summary still reads as the sheet; `onCase` fires in **completion** order, which is the point of it — combined with the queue above, the first finished row is running while the others are still being written. Narration is prefixed `[<caseId>]` only when workers > 1; `1` is the sequential loop and the A/B. The cost is model pressure: three calls in flight against a free tier trips rate limits sooner, and the failover/breaker machinery is what absorbs it.

**Output is tagged per case only when cases run beside each other** — `[c3]` on every line of case 3, applied per line so a multi-line summary cannot arrive half attributed, one `write` per call. A roster (`  [c1]  alone|shared  <name>`) prints before anything runs. `jobs.ts` demultiplexes the tags into `Job.cases` — each with its own denominator, lines and verdict — and wowUI renders one row per case with its own progress bar and a collapsible output pane; the polled list and the SSE stream shed per-case lines (a running case's output is demultiplexed client-side from the job stream already arriving), and only a case *changing state* triggers a re-render, so step progress costs no DOM churn and an open pane keeps its scroll.

**Runs are grouped by the authoring pass, and a re-run stays in its group.** wowUI groups on `generatedBy.generatedAt` (identical across one pass, different for the next — running the same catalog twice is two groups, never twelve runs of a six-case catalog with a pass rate averaged over two builds), titled by `GenerationProvenance.source` (the document's file name; the login page's URL was the same for every catalog anyone had ever run). `Flow.authoredBy` writes the same provenance **into the flow file, before it is written**, so `wow run x.flow.json` and a `.attempt-N` repair report the pass that authored them and land in its group rather than under "Authored flows". Group headers collapse on the ▾, keyed on the batch so a poll cannot spring one open.

**Autoheal (`--repair` on a suite) heals each case through the same `FlowRepairLoop` that `run --repair` uses.** The loop runs the first attempt itself, so a clean pass costs exactly one run; on a failed / error / dead-end outcome the repair model rewrites the flow around the break and the case reruns, up to `--repair-attempts` total, each rewrite landing as its own reviewable `.attempt-N.flow.json` + `.patch` beside the case's artifacts. Gated once per suite on the generator role resolving a key — when it cannot, the suite says so and runs exactly as before rather than failing every case on a missing key. Surfaced in wowUI as the launcher's **Autoheal enabled** checkbox (in front of the advanced fold; `extras.repair`), and on the `go`/`run`/`generate`/`catalog-run` command specs.

### Reading the document (`src/catalog/extract.ts`)

Markdown, CSV, HTML, text, JSON, YAML, **Excel, PowerPoint and PDF** — and the binary formats are parsed here rather than by a dependency. A `.pptx` is read through the same central-directory ZIP reader as a workbook: one `ppt/slides/slideN.xml` per slide, `<a:t>` runs joined per `<a:p>` paragraph (a title split by formatting stays one line), speaker notes carried under a `(speaker notes)` label — the author talking, not the slide asserting — and an all-image deck refused with the cause named, the PDF-with-no-text-layer rule again. Fixture written by Python's zipfile, an independent writer. Each is a container this needs one narrow thing from (cell strings; text-showing operators), and a library that can render a spreadsheet or rasterise a page is a lot of surface to carry into a test framework for that. `node:zlib` supplies the only hard part.

**The rule that outranks the formats: never hand back text that is not in the document.** This is the one step where a silent mistake is invisible downstream — a model asked to write tests from mangled text writes plausible tests about nothing, and the claims, the steps, the run and the green report all inherit the error while looking exactly like success. So an unreadable format is **refused by extension, not sniffed**; a PDF with no text layer **throws** naming the likely cause instead of returning a scan's stray characters; and anything approximated comes back on `note`, which the CLI prints and the UI shows rather than logging.

Four details found by running it against real files:

- **Only what sits between `BT` and `ET` is a PDF's text.** An embedded ICC profile or font program inflates just as happily as page content and is full of bytes that look like string operands. Scanning whole streams turned a three-line checklist into three lines followed by 15,000 characters of mojibake.
- **PDF fonts are not read.** A custom encoding yields plausible-looking nonsense rather than an obvious failure, so `garbledNote()` warns when too much of the result is outside the scripts this codebase expects. One wrong em-dash is not worth a warning; a page of them is.
- **A ZIP is read through its central directory**, never by scanning for local headers: a local header's sizes may be zero with the real values in a trailing data descriptor, and a scanner that trusts them walks into the middle of a compressed stream.
- **A sparse spreadsheet row keeps its column letters.** A row with values in A, D and Q is not a three-column row, and flattening it would move data under the wrong heading.

There is a real `.xlsx` (written by openpyxl) and a real `.pdf` in `tests/fixtures/`: a ZIP reader tested only against its own writer proves the two agree, not that either is right.
