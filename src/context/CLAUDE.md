## Understanding a page beyond its first render (`src/context/page-probe.ts`)

Every reader in wowlidator reads one AX tree, captured once, of the page as it loaded. That is right by default and has a hard limit: an application's most important controls are frequently one click away from *existing*. A generator pointed at a page whose role switcher lives behind an identity menu cannot write a role-switching test, because at the moment it looked, the menu items were not in the document — it writes a smaller test, and the reason is invisible.

`probeInteractions()` opens each disclosure, records what appeared, closes it, and hands the result to the prompt as a clearly-labelled separate section. Opt in with `--probe` (CLI) or `probe: true` (`TestGenerator`/`FlowAuthor`); omit it and generation is byte-for-byte what it was.

**Only ARIA-marked disclosures are ever clicked** — `aria-haspopup`, `aria-expanded="false"`, `role="combobox"` — never a bare button. This is the safety model, not a heuristic: "Submit", "Delete" and "Approve" carry none of those attributes, so they are not candidates. It is the same understate-never-overstate rule `ax-coverage.ts` applies to attribution, pointed at a much riskier operation — a missed disclosure costs coverage, a mistakenly clicked *action* writes to someone's database. There is a test asserting a destructive button is never clicked; keep it.

**Provenance is kept separate from the tree.** "Behind this menu" and "on the page" are different claims, and a model that conflates them writes a flow that clicks a menu item without opening the menu. `formatProbeReport()` says `click "X" reveals:` and the request carries it in its own field.

**Each probe is verified closed before the next one opens.** A dialog that ignores Escape would put its contents in the next control's results, so probing stops there and says why. A capped run reports how many disclosures it did not open — a truncated probe otherwise reads exactly like a page with nothing more to show.

**One level deep, on purpose.** The probe opens a menu, not the dialog that menu's item opens. Two-level probing multiplies the clicking on a live application for a rapidly diminishing return, and the second level is exactly where destructive controls start appearing.

## The capture pilot (`src/context/capture-pilot.ts`)

The AX tree generation and authoring read is a photograph, and the deterministic settles (`load`, `networkidle`, the lazy-content walk, `document.fonts.ready` + double-RAF in `evidence.ts`) can only wait for things a heuristic can *name*. What they cannot do is look: a skeleton screen is "loaded" as far as the network is concerned, a spinner outlives `networkidle` on a polling app, a cookie banner covers the controls that matter. Before a generate/author capture, the workflow agent briefly takes the browser with a deliberately narrow goal — wait out loading states, dismiss blocking overlays, scroll once for lazy content, **then stop** — and the capture that follows is the evidence, whatever the pilot claims. Same "prepare, never perform" contract as the ladder's agent rung.

- **On by default, `--no-agent-capture` disables** — unlike `--probe`/`--agent-assist`, because the pilot's goal forbids navigation, form submission, data changes and menu-opening (disclosures are the probe's job — two features clicking the same menus would double a risk the probe's design already paid for once), and because an inaccurate capture poisons every test written from it.
- **Degrades silently to an unpiloted capture** when the agent role has no key (`buildCapturePilot` returns null) — a capture without a pilot is the capture we always took.
- **Bounded hard**: `CAPTURE_PILOT_MAX_STEPS` (5). A pre-flight check, not an exploration.
- A broken pilot never breaks a capture — `pilotCapture` never throws, and the capture proceeds regardless.

## Retrieval and the token bill (`src/context/retriever.ts`)

Every "which part of this evidence does the model need" decision goes through one seam. `Retriever` is the pluggable interface (async on purpose — an embedding ranker is a request; BM25 just answers), `Bm25Retriever` the only implementation, `buildRetriever()` the factory (`WOWLIDATOR_RETRIEVER`, unknown values fail at the boundary). It reuses the same `relevance.ts` BM25 the catalog/table/route retrieval already measured (94% less background per row, 386 tables → 9), and its rules are enforced in the module, not re-decided per caller: under the budget nothing happens, document order is restored after ranking, and a cut is disclosed with wording that forbids reading absence into it.

`focusTreeText()` is the tree-as-text form of the agent's `focusTree`, for callers that hold a rendered tree: the **healer** ranks its 120-node capture down to `HEAL_TREE_MAX_LINES` (60) against the failed selector + intent + case card (measured 3.2k input tokens per heal, most of it controls the intent never named — and the blind capture cap could leave the answer past the cut, which ranking cannot); the **author** ranks the per-row journey tree against the row's own request (`JOURNEY_TREE_MAX_LINES`, label line always kept, and the narrowed text is also what the grounding lints read — model and lints see one tree). The **start tree is deliberately never narrowed per row**: it is the page the first steps are written against and the one section shared across a catalog's rows.

**Prompt order is the token bill.** Each agent turn is a stateless single-shot call, so the only discount is a provider's implicit prompt cache, which bills the longest byte-identical *prefix* at cache rates. The agent's turn prompt is therefore ordered stable-first — goal, case card, tree — with everything that changes every turn (URL, history, feedback) after; the old order put the growing history in front of the ~3.3k-token tree, so the dominant repeated bytes (2.14M input across 560 turns on be100) never cached. The healer's re-ask and the author's feedback retry already follow the same rule.

**`Flow.caseContext` is how the runtime roles know what a step proves.** The catalog path stamps a bounded card (`caseCard()` in `commands/authoring.ts`: case id, expected output, test data, persona, and the Note column — where a sheet says "Cancelled" or "KNOWN FAIL") into the flow file, the `authoredBy` rule; `runFlow` threads it to every heal (`HealRequest.caseContext`) and every agent turn (`RunOptions.caseContext`). Context, never instructions: the goal and the claim stay the only things pursued, but a model that knows the claim stops spending turns rediscovering what the spec already states. Both prompts label it as context outright.

## Repository context engine (`src/context/`)

Generation and healing default to seeing *one page* — an AX tree, nothing else. The context engine is a second, complementary source: a static index of the *project*, so a prompt can be told what a route renders and what already tests it without spending a token to find out.

Deliberately not an AI feature — this is where "AI should only be used where reasoning is required" actually draws a line: indexing is not reasoning, so `ContextEngine.build()` never calls a model, only `readdir`/`readFile` and a real parse. That parse is `@babel/parser`, not the TypeScript compiler — see the comment atop `component-ingester.ts` for why: this repo's own `typescript` devDependency is pinned to the v7 native rewrite, whose public surface no longer exposes the classic `createSourceFile`/`forEachChild` API a walk like this needs, only an early "unstable" service-based one tied to that exact version. A dedicated, stable, synchronous parser that doesn't move whenever the host project's own compiler does is the right call for something meant to run against arbitrary target repositories, not just this one.

Four ingesters, each independent and pluggable (`Ingester` in `types.ts`): manifest (`package.json`/`tsconfig`/`README`), component (React/JSX usage via real AST, not regex), route (Next.js App Router and Pages Router file conventions), and test (existing test titles, plus — because it's *our own* format and therefore actually readable — the URLs a `.flow.json` navigates to). `ContextEngine.build()` merges their output, and two rules carry over from elsewhere in this codebase rather than being reinvented:

- **An edge whose endpoint was never indexed is dropped, not guessed at.** Same "understate, never overstate" rule as `ax-coverage.ts`'s attribution honesty. A route ingester's guess at which component a page renders is only ever a guess at an *id* — if the component ingester didn't independently produce a node with that exact id, the edge is pruned in the merge step, not kept as a maybe.
- **A crashing ingester doesn't take the graph down with it.** Its warning lands on `graph.sources`, the other three still run — same reasoning as history/coverage being diagnostic and swallowed rather than failing a run.

**The prompt slice is seeded by the description, not only by the starting URL** (`routesForDescription`, `query.ts`). A journey starts on one page and is *about* another: `go "log in, then create an overtime request" --url /en/login --repo …` walked outward from the login route and handed the authoring model **two lines** — while 71 nodes describing overtime sat unread in the same 1,874-node graph. Routes are now ranked against the author's own words with the same BM25 primitive the catalog retrieval uses (`src/context/relevance.ts`, one tokeniser and one idf for both callers), and the description-matched roots seed the same capped walk. They are **labelled apart** from the start route — "pages elsewhere in the application, not the page you are on" — because a flow that confuses the two clicks its way to a page it never opened, the probe-report separation rule again. `ROUTE_SCORE_FLOOR` keeps a route that shares one generic word with the description out of it, the same instrument and value as `RELATIVE_SCORE_FLOOR`.

Measured against that exact saved invocation, authoring the same prompt with and without `--repo`:

| | grounded | ungrounded |
|---|---|---|
| backend claim | `dbSnapshot` + `expectDbDelta +1` on `time_management.ot_request` | none — the model's own note: *"omitted as no specific database table names were declared in the prompt"* |
| destination | the workflow goal names `/en/time` and `/en/overtime` | "Time and Attendance page", a label with no route behind it |
| prompt | 56,237 input tokens | 4,318 |

The prompt never named a table or a route. That is the whole point of the feature — **the parts of a journey the description does not spell out come from what the codebase declares** — and the cost line is the honest other half: grounding is not free, and the 386-table inventory is most of it.

`covers` edges are a second pass after merge (`linkCoverage`): a flow's recorded URLs are matched against route name patterns (`:id`, `*catchAll`), so the graph can answer "does anything already test this route?"

**Caching is a cheap composite signature, not per-file content hashing.** Every walked file's size and mtime feed one hash (`computeSignature`); a match short-circuits straight to the cached graph in `.wowlidator/context-graph.json` without touching an ingester. Content-hashing every file on each `generate` call would cost more than the parse it's meant to avoid repeating.

Wired into the generator additively: `TestGeneratorOptions.projectGraph` and `GenerateRequest.projectContext` are both optional. Omit them and generation is byte-for-byte what it was before this existed. When a graph is supplied, `toPromptContext()` walks outward from the URL's matched route — capped at `DEFAULT_CONTEXT_MAX_NODES`, same token-budget reasoning as `DEFAULT_MAX_AX_NODES` — never the whole graph. The CLI and MCP surfaces mirror this: `--context` / `context: true` opt in per call, `wowlidator context build`/`show` manage the graph on its own.

**The journey capture reads where the request says it goes, in this order of evidence.** (1) A URL or path the request names outright, on the run's origin (`literalDestinations` — a test-case row frequently says "Go to http://…/employees/EMP-0005/probation" in so many words, and the ranker was choosing `…/:id/change-type` from the same words); (2) **the application's own menu** — `NavMap`, learned once per repository from a signed-in shell by `learnNavigationMap` (the shell's links plus what its ARIA disclosures reveal; on the measured app one collapsed rail holds the whole menu, 19 links, "Probation Reviews" → `/en/workflows/probation` among them), remembered on the registry entry, and consulted through `navDestination` (first leaf named in the row's Menu column wins — a rail's group names are buttons, not links); (3) ranked routes, tried in order until one resolves, `:id` filled from an id-shaped token in the request (`fillRouteIds`) or the next candidate taken. The measurement that forced (2): BM25 over the code ranked the wrong route on **6 of 6 rows** of a human-worded catalog, because "Team → Probation Reviews" shares no token with `/:locale/workflows/probation` and `queryTerms` caps a described row at 200 terms in order of first appearance, past which its steps fall. **The capture is per row on the catalog path** (it was `wow go "text"`-only, so `--scope e2e` — also never handed to the catalog's author — captured nothing and every case's middle went to a `workflow` step), it reports the **observed sign-in landing URL** as evidence for the one assertion the author otherwise guesses, and it leaves the shared context as it found it (a sign-in performed for the capture is undone before the tab closes, or every isolated run inherits it). The grounding lints (`ungroundedUrlExpectation`, `ungroundedCountRole`) read **every tree the model was given**, journey tree included — they refused an `expectUrl` the queue's own Review link grounded, three times, on the row the capture had been added to help. `context add --db-schema <path>` resolves the path at the command boundary (`bin/wow` treats `--db-schema` as a path flag): a schema typed relative to the caller's directory was being resolved against the target repository, indexing zero tables with a warning nobody read.

**A repository remembers context documents, not only code** (`RepoEntry.contextDocs`, `mergedContextDocs`). `wow context add <repo> --context-doc <file>` (markdown, text, PDF, PowerPoint, Excel, CSV — validated at the command boundary, stored absolute) attaches background to the entry, and every catalog run grounded in that repo reads it automatically, deduplicated against per-run `--context-doc` flags. Two update paths, both deliberate: the registry stores the *path*, never a copy, so editing the file on disk updates the context by itself; and re-adding a file of the same name replaces the remembered path — an updated spec supersedes the old copy instead of lingering beside it. A re-add also preserves `nav` and the remembered docs, the `mergedScanInputs` rule. wowUI: **Remember document…** per repository row (uploads into `.wowlidator/context-docs/`, then re-registers), remembered names listed under the path.

OpenAPI is the fifth ingester (`openapi-ingester.ts`), producing `operation` nodes — one per method+path, because two operations can share a path and `GET /orders` and `DELETE /orders` are different promises. `linkCoverage` matches them against the `METHOD url` pairs a flow's `request` steps record, so the graph answers "does anything already test this endpoint?" the same way it answers it for routes. **The method must match exactly**; crediting a `GET` against a declared `DELETE` would overstate coverage in precisely the way `ax-coverage.ts` refuses to.

**What it doesn't cover yet, on purpose, not by omission:** Vue Router, Angular's `RouterModule`, SvelteKit, Storybook, GraphQL schemas, OpenAPI `$ref`s that point outside the document (recorded as unresolved rather than guessed at), and Playwright/Cypress/Jest/Vitest test bodies beyond their `describe`/`it` titles (their bodies are opaque — arbitrary code, not a format we own the way `.flow.json` is). The `Ingester` interface is what makes adding one of those an additive, single-file change rather than a redesign — any file in `src/context/ingesters/` shows the shape.

## The database hint (`src/context/db-hint.ts`)

A scan learns the database's *schema* (tables, via `--db-schema` or live introspection through wowlidator's own `WOWLIDATOR_DB_URL`) but knew nothing about the *connection* — asked live (2026-08-25): "does scanning the repo make the system know the database is postgres at 5432?" It did not. `detectDbHint()` closes that as a HINT read from the scanned repo's own files, best source first: a dotenv DSN (`.env`, `.env.local`, `.env.development`, `.env.example`; keys matching `DATABASE_URL` and friends, plus whatever var a Prisma datasource names), then a compose file's database service (engine from `image:`, the *published* port — host is `localhost` on purpose, the hint is for connecting from the machine running wowlidator). Two rules are load-bearing: **a secret never leaves the file it lives in** (a password is reported as a location — `.env.local: DATABASE_URL (password present — not read)` — never a value, and `suggestedUrl` is built without one; the person sets `WOWLIDATOR_DB_URL` themselves), and **a hint is never a connection** (nothing here opens a socket — file-walk-and-parse, unit-tier, same as the rest of the engine). Stored on `RepoEntry.dbHint` at `context add`/`build`, shown by the panel's Database card next to "no database configured". A file too odd to parse yields no hint rather than a wrong one.
